## 3. 权限模型（核心）

### 3.1 三层结构

```
角色(role)  ──映射──▶  权限组(perms)  ──其中含──▶  数据范围(scope)
```

定义集中在 `backend/app/permissions.py`，接口层只声明需要哪些权限组，不再散落 role 字符串判断。

```python
# 14 个功能组 + 4 档数据范围（2026-09 细化后）
PERM_GROUPS = {
    "apply": "在线报名", "audit": "信息审核", "import": "批量导入",
    "export": "汇总导出", "analysis": "数据分析", "exam_manage": "考试批次管理",
    "dict_manage": "字典与考试类型维护", "user_manage": "用户与权限管理",
    "dashboard": "数据看板", "idphoto": "证件照制作",
    "realname": "实名认证（本人填报）", "realname_audit": "实名信息审核",
    "ai": "AI 助手", "system_manage": "系统维护",
    "scope_class": "数据范围：本班级（可多班）", "scope_grade": "数据范围：本年级",
    "scope_college": "数据范围：本院系", "scope_all": "数据范围：全校",
}

FUNC_GROUPS = ["apply", "audit", "import", "export", "analysis",
               "exam_manage", "dict_manage", "user_manage", "dashboard",
               "idphoto", "realname", "realname_audit", "ai", "system_manage"]

ROLE_PERMS = {
    "candidate":        ["apply", "idphoto", "realname", "ai"],
    "head_teacher":     ["apply", "import", "export", "analysis", "dashboard",

    "college_reviewer": ["audit", "export", "analysis", "dashboard",
                         "realname_audit", "idphoto", "ai", "scope_college"],
    "reviewer":         ["audit", "export", "analysis", "dashboard",
                         "realname_audit", "idphoto", "ai", "scope_all"],

                         "exam_manage", "dict_manage", "user_manage", "dashboard",

                         "system_manage", "scope_all"],

```

细化后每个业务模块都有自己的权限组，不再「借」别人的组
（早先字典维护挂在 `exam_manage` 下，能建批次就等于能改全校字典）。
老账号升级时按 `PERM_MIGRATE_MAP` 补组：

```python
PERM_MIGRATE_MAP = {
    "dict_manage":    ("exam_manage",),   # 以前靠批次管理进字典页
    "system_manage":  ("user_manage",),
    "realname_audit": ("user_manage",),
}
```

`db._migrate_perm_groups()` 在 `init_db()` 里跑：给单独授权过的账号补齐这些组，
并统一补上 `idphoto` / `realname` / `ai`（考生本就该有）。

每个功能组都在 `GROUP_DESC` 里配了一句话说明，经 `describe()` 的 `perm_detail`
下发到授权页 —— 管理员面对的是「批量导入：批量导入报名数据与证件照
（仍受本人数据范围约束）」，而不是一串猜不出边界的名词。

### 3.2 接口声明方式

```python
from ..permissions import require_perms

@router.get("/api/applications")
def list_apps(user=Depends(get_current_user)):
    frag, params = scope_filter(user, "applications_computer")
    rows = db.query(f"SELECT * FROM applications_computer WHERE 1=1{frag}", params)
```

- `require_perms("import")` —— 缺权限直接 403，错误信息里带中文权限名
- `require_admin()` —— **只看角色、不看权限组**。用户管理（`/api/users/*`）全部用它：
  单独授权只能分配「功能」，不能让人获得改别人账号的能力，
  否则管理员把 `user_manage` 勾给某个非管理员就等于变相提权
- `scope_filter(user, table)` —— 返回 `(" AND class_name IN (?,?)", ["计算机2101","软件工程2202"])` 这样的片段，
  追加到任意 WHERE 子句即可完成数据范围收敛（班主任多班级按 IN 匹配）

### 3.2.1 单独授权（按用户覆盖角色默认权限）

角色给的是「默认值」，管理员可对单个账号逐个开关功能（`users.perms`，JSON 数组）：

```python
FUNC_GROUPS = ["apply", "audit", "import", "export", "analysis",
               "exam_manage", "dict_manage", "user_manage", "dashboard",
               "idphoto", "realname", "realname_audit", "ai", "system_manage"]

def effective_perms(user):
    stored = _stored_perms(user)      # None=未配置；[]=已配置但全关
    return stored if stored is not None else perms_of(user["role"])
```

要点：

- **`perms` 列必须出现在 `deps.get_current_user` 的显式列清单里**，否则登录态拿不到，
  会静默退化成角色默认值（此前新增 `classes` 列时踩过同样的坑）。
- **数据范围不参与功能开关**：`scope_*` 由 `scope_of()` 单独判定，
  避免关掉功能后数据不可见或越权。
- 语义唯一：传来的 `perms` 就是最终生效值。
  与角色**功能项**完全一致时自动清空（恢复跟随角色）；传 `[]` = 有意关闭全部功能，不再回退。
  比对要用 `role_func_perms()`（剔除 `scope_*`），否则「恢复默认」分支永远不可达。
- 接口：`GET /api/users/{id}/perms`（返回逐项开关）、`PUT /api/users/{id}/perms`。
  管理员不可修改自己的权限（防误关后无法恢复）。
- **`has_perm()` 对 `scope_*` 前缀特判按角色判定**（见 §3.2）。`users.perms` 只存功能项，
  若 scope 也走 `effective_perms()`，单独授权过的账号会丢失 `scope_all`，
  导致分析 `scope` 降级为 `class`、列表按班级收敛（真实踩到，已由
  `tools/verify_scope_fix.py` 覆盖）。
- **前端权限不能只认登录快照**：会话把用户对象（含 `perms`）存在 localStorage，
  管理员改权限后对方若不重新登录，菜单会停留在旧权限。`app.js` 在路由守卫里按 token
  缓存地调一次 `/api/auth/me` 刷新（`refreshMe()`），被关闭的页面会自动跳回首页。

新增权限相关字段时，需同步：`permissions.py` → `deps.py` 列清单 → `auth._public_user`
→ `users.public_user` → 前端 `users.js`。

### 3.2.2 数据范围逐账号覆盖（`users.scope`）

与功能开关并列的第二层覆盖：管理员可对单个账号**收窄**数据范围，但**不得放宽**
（放宽即提权）。

```python
def role_scope(role):                  # 角色默认档位 = 该角色拥有的最宽一档
def allowed_scopes(role):              # 可选档位 = 级别 <= 角色默认档位
def scope_of(user):                    # 生效档位：单独设定若超过角色上限则回退
```

- `users.scope` 空串 = 跟随角色；`PUT /api/users/{id}/perms` 传 `scope` 一并保存，
  超过 `allowed_scopes(role)` 直接 400（前端下拉也只列可选档位，从源头杜绝）。
- `has_perm()` 对 `scope_*` 前缀特判，走 `scope_of(user)` 而不是 `effective_perms()`。
- `scope_grade` 依赖报名表**没有**的年级列，只能关联 `users` 取同年级班级：
  `class_name IN (SELECT class_name FROM users WHERE grade=? AND class_name<>'')`。
  局限与对策：报名表没有年级列，只能落在考生账号上。**批量导入已支持「年级」列**
  （`grade` 是 import_map 里的虚拟字段，只写账号、不写报名行），也可用整批 `defaults`
  指定；导入时若关闭「同时创建考生账号」则无账号可挂，这一档仍会漏（文档已注明）。
- **踩坑**：`scope_of()` 曾在同文件里被二次定义，后写覆盖先写，导致新档位静默失效
  （`college_reviewer` 拿到 `none`）。修改 `permissions.py` 后务必全文搜重名函数。
- **踩坑**：`_normalize_scope()` 过去对非范围角色强行清空 `grade/classes`，
  使「把审核员收窄到本年级」没有依据字段。现改为保留（未收窄时不参与过滤，不越权）。
- **写操作同样要过范围守卫**：`_do_audit()` 在改状态前调 `_scope_guard(user, tbl, app_id)`，
  二级学院审核即便手工构造「别的院系」的记录 ID 也审核不了（返回 404）。
  已由 `verify_college_scope.py` 覆盖，并做过**反向验证**（临时注释掉守卫 → 该用例 2 项失败）。

### 3.3 数据范围映射

| scope | 过滤字段（computer / mandarin） |
|---|---|
| `scope_all` | 无过滤 |
| `scope_college` | `school`=院系（普通话表为 `department=`），取自用户 `college` |
| `scope_grade` | `class_name` IN (同年级班级子查询)，取自用户 `grade` |
| `scope_class` | `class_name` IN (用户 `classes` 列表，逗号分隔，可多班) |
| `none` | `AND 1=0`（只通过 `user_id` 看自己的） |

院系列名差异由 `_college_column(table)` 统一处理（普通话模板叫 `department`，
计算机模板叫 `school`）。范围未配置时一律返回空集（`AND 1=0`），
避免"有权限但越权看全部"。

各角色默认档位与可收窄上限：

| 角色 | 默认 | 可单独设定 |
|---|---|---|
| 管理员 / 审核员 | 全校 | 本班级 / 本年级 / 本院系 / 全校 |
| 二级学院审核 | 本院系 | 本班级 / 本年级 / 本院系 |
| 班主任 | 本班级 | 本班级 |
| 考生 | 仅本人 | — |

### 3.4 权限组核验

`GET /api/users/verify` 逐账号核对「角色 → 权限组 → 数据范围」是否自洽，

### 3.5 证件照存储与批量匹配

**存储**：文件落盘 `data/photos/u{用户ID}.{ext}`，`users.photo` 只存文件名。

- 不让 SQLite 膨胀（几千张 × 几百 KB 会让库文件与备份迅速变大）
- 文件名不含身份证号等敏感信息，也不会出现在日志里
- 规避中文文件名在 Windows 上的编码问题

**读取**：`GET /api/photos/{user_id}`，服务端查库映射真实文件，前端拿不到存储路径，
天然杜绝路径穿越。鉴权：本人，或具 `user_manage` / `audit` / `import` 权限者（审核需核对身份）。

> 读取接口要带鉴权头，`<img src>` 带不了，所以前端统一取回 blob 再转 objectURL，
> **不把令牌拼在 URL 上**（避免泄漏到地址栏、代理与访问日志）。

**安全校验**：类型以 **magic bytes** 判定（JPEG `FF D8 FF` / PNG `89 50 4E 47`），
不信扩展名、不信 Content-Type；单张 ≤ 5 MB。

**批量导入匹配**（文件名去掉扩展名后依次尝试）：

| 优先级 | 字段 | 命中多人时 |
| --- | --- | --- |
| 1 | 证件号码 | 唯一索引，理论不会重复 |
| 2 | 用户名 / 学号 | 唯一 |
| 3 | 手机号 | 判为 ambiguous，跳过 |
| 4 | 姓名 | **判为 ambiguous，拒绝覆盖** |

重名绝不猜测——宁可跳过并提示改名重传，也不能把 A 的照片盖到 B 头上。
流程为 **预览 → 确认**：预览把匹配结果落盘为 `meta.json`，确认时以预览为准，
避免「预览 A、覆盖 B」；同一 token 不可重复使用。

> 关联修复：原先 `users.id_number` **没有任何写入入口**（建号 / 编辑都不支持），
> 导致「按证件号匹配」形同虚设。现已给 `UserCreateIn` / `UserUpdateIn` 加上
> `id_number`，并复用 `app/validators.py` 做合法性校验。
>
> **还有一处更隐蔽的漏点**：批量导入建号走的 `_ensure_student_user()` 也没写
> `id_number`。后果有两个——①「按证件号匹配照片」对导入生全部落空（这是该功能的主路径）；
> ② 该函数靠 `id_number` 做同一考生查重，库里是空值 ⇒ **每次导入都建新账号**。
> 现已写入，并对历史账号做兜底：按派生用户名（`s` + 证件号后 8 位）找回并补写
> `id_number`，避免老数据重复建号。新增 `grade` 参数一并落库。

### 3.6 一键导出证件照

`GET /api/photos/export/stat`（数量预览）与 `POST /api/photos/export`（打包下载），
入参 `exam_id` / `fmt`(jpg|png) / `audit_status` / `class_name`（空 = 全部）。

- **目录**：`{考试批次}/{院系}/{班级}/{证件号码}.{jpg|png}`，三级目录由
  `_safe_name()` 清洗（去 Windows 非法字符与收尾点号，空值落「未填写」）
- **院系列名差异**复用 `_college_column(table)`（计算机 `school`、普通话 `department`）
- **格式转换** `_convert_image()`：已是目标格式原样返回（不重编码）；
  PNG→JPG 时透明通道铺白底再存 JPEG，否则 Pillow 直接报错
- **zip 中文名**：`ZipInfo.flag_bits |= 0x800` 标记 UTF-8，否则 Windows 解压乱码
- **缺照片不中断**：记入包内《_导出说明.txt》（姓名/证件号/院系/班级/原因），
  整批 0 张时才返回 400
- 写入临时文件后 `StreamingResponse` 分块返回并在结束时删除；`_cleanup_export_tmp()`
  兜底清理 1 小时前的残留
- **按班级分批**：`class_name` 参与 `_export_rows()` 过滤；`_distinct_classes()` 返回
  **数据范围内**的去重班级，随 `stat` 的 `classes` 字段下发供前端下拉
  （二级学院审核员只见本院系班级），用于超上限时分批
- **文件名清洗**：证件号虽已受 `ID_RE`（字母数字 6–30）约束，仍过一遍 `_safe_name()`
  再拼 zip 路径，避免将来放宽校验后拼出越界路径（纵深防御）
- 权限 `export` + `scope_filter()` 收敛；单次上限 5000 条，超限提示按班级或审核状态分批

## 4. 考试类型（内置模板 + 管理员自定义）

### 4.1 核心约定

```
exams.exam_type   → 存「类型编码」：面向用户，可自定义（如 english）
各处 app_type     → 存「基础模板」：computer / mandarin
```

**基础模板**决定：

| 决定项 | computer | mandarin |
| --- | --- | --- |
| 存储表 | `applications_computer` | `applications_mandarin` |
| 采集字段 | 13 个 | 20 个 |
| 校验器 | `validate_computer` | `validate_mandarin` |
| 官方导出模板 | 计算机类 | 普通话 |
| 院系列 | `school` | `department` |

因此**新增一个类型 = 选一个基础模板 + 起名称与编码**，报名 / 导入 / 审核 / 导出 / 分析
整条链路直接复用，不需要新增代码。

### 4.2 数据模型

```sql
CREATE TABLE exam_types (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    code TEXT NOT NULL UNIQUE,             -- 小写字母开头，2-30 位，创建后不可改
    name TEXT NOT NULL,                    -- 显示名，随时可改
    base_type TEXT NOT NULL CHECK (base_type IN ('computer','mandarin')),
    description TEXT DEFAULT '',
    fields_config TEXT DEFAULT '',         -- JSON：{"subject":{"enabled":true,"required":true,"label":"报考科目"}}
    enabled INTEGER NOT NULL DEFAULT 1,
    is_builtin INTEGER NOT NULL DEFAULT 0, -- 内置两套不可删除
    sort INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

### 4.3 解析模块 `backend/app/exam_types.py`

单一事实来源，缓存 `code → row`，CRUD 后调 `refresh()` 失效：

| 函数 | 用途 |
| --- | --- |
| `base_type_of(code)` | 编码 → 基础模板（未知编码兜底 `computer`） |
| `label_of(code)` / `field_label(code, field)` | 类型名 / 字段显示名 |
| `fields_of(code)` | 实际采集字段（去掉被关闭的） |
| `required_of(code)` | 系统必填 ∪ 管理员追加 |
| `fields_meta(code)` | `[{key,label,enabled,required}]`，供前端渲染表单与详情 |
| `college_column(code)` | 院系列名（`school` / `department`） |

> **同一字段在两套模板里叫法不同**（`name`：计算机「姓名」、普通话「考生姓名」），
> 因此标签取 `BASE_FIELD_LABEL[base]`，不能用单一全局字典，否则报名表单会被通用标签覆盖。

### 4.4 接口 `backend/app/routers/exam_types.py`

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/exam-types` | 全部类型（含字段配置），登录即可读 |
| GET | `/api/exam-types/options` | 启用中的类型下拉（`value` / `label` / `base_type`） |
| POST | `/api/exam-types` | 新建（`exam_manage`） |
| PUT | `/api/exam-types/{id}` | 改名 / 改字段 / 启停（`exam_manage`） |
| DELETE | `/api/exam-types/{id}` | 删除；内置或使用中拒绝（`exam_manage`） |

`_clean_config()` 做三件事：丢弃模板不存在的字段、截断标签到 30 字、**强制系统必填项开启且必填**。

### 4.5 字段配置如何在写入链路生效

| 环节 | 生效方式 |
| --- | --- |
| 报名表单 | `GET /api/exams/{id}` 返回 `fields`，前端按 `enabled` 决定是否渲染、按 `label` 显示、按 `required` 生成校验规则 |
| 服务端校验 | `validate_computer/mandarin(body, code=...)`：关闭采集的字段清空且不校验；必填集合 = 模板固定必填 ∪ 管理员追加 |
| 批量导入 | 预览的可映射字段与必填标记、整批默认值的可用字段，均按类型配置过滤 |
| 导出 | 表头与列集合按 `fields_of(type)` |
| 审核 / 我的报名 | 详情返回 `fields`，前端只展示开启字段并使用自定义名 |
| 数据分析 | `build_scope()`：选基础类型时包含所有基于该模板的子类型；选自定义类型时只统计该类型批次 |

### 4.6 兼容要点

- `exams` / `audits` 上原有的 `CHECK (… IN ('computer','mandarin'))` 由 `_drop_type_checks()`
  检测并重建表移除，老库升级不丢数据
- 内置两套类型由 `_seed_exam_types()` 播种（`is_builtin=1`）
- `exams.py` 里的 `TYPE_LABEL` 是 `dict` 子类，`__getitem__` / `get` / `__contains__` / `items`
  都回查 `exam_types` 表，历史调用点对自定义类型同样成立，无需逐个修改
- 停用类型只阻止**新建批次**，已建批次继续可用（报名 / 审核不受影响）

### 4.7 通用模板（第三套基础模板，支持自定义字段）

除计算机 / 普通话两套**字段固定**的模板外，系统新增 `generic`（通用考试报名）模板：
只保留 8 个各类考试通用的核心字段，**其余字段由管理员在「考试类型管理」里自行设计**，
不需要改程序即可适配英语四六级、教师资格证、职业技能等级认定等任意考试。

```
基础模板决定项        computer           mandarin        generic
────────────────────────────────────────────────────────────────────
存储表                applications_c…    applications_m… applications_generic
采集字段              13                 20              8 固定 + N 自定义
自定义字段            ✗                  ✗               ✓（exam_type_fields）
官方导出模板          计算机类           普通话          自定义表头
院系列                school             department      college
```

**数据模型**：

```sql
-- 自定义字段定义：每个通用类型一套
CREATE TABLE exam_type_fields (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    type_code TEXT NOT NULL,        -- 关联 exam_types.code
    field_key TEXT NOT NULL,        -- ^[a-z][a-z0-9_]{1,29}$，且不得与固定字段重名
    label TEXT NOT NULL,            -- 显示名
    field_type TEXT NOT NULL,       -- text/textarea/number/date/select/multiselect
    required INTEGER NOT NULL DEFAULT 0,
    options TEXT DEFAULT '',        -- select/multiselect 的选项，JSON 数组
    placeholder TEXT DEFAULT '',
    sort INTEGER NOT NULL DEFAULT 0,
    UNIQUE (type_code, field_key)
);

-- 报名行：固定字段各占一列，自定义字段的值整体存 extra(JSON)
CREATE TABLE applications_generic (
    ... , extra TEXT DEFAULT '', ...
);
```

**为什么自定义字段存 JSON 而不是加列**：通用模板的字段由管理员随时增删，
若按字段加列就得在运行时 `ALTER TABLE`，且老库升级、导出列序、跨类型统计都会变复杂。
`extra` 存 JSON 的代价是**不能按自定义字段做 SQL 聚合**——但自定义字段本来就不参与
字典筛选与排行（分析 / 大屏只统计固定字段），因此代价可接受，换来的是零迁移成本。

**校验链路**（报名提交与批量导入共用同一套）：

| 字段类型 | 校验规则 |
| --- | --- |
| text / textarea | 长度 ≤ 200 / 2000 |
| number | 必须是数字，允许小数 |
| date | `YYYY-MM-DD` 或 `YYYY/MM/DD`，且日期真实存在 |
| select | 取值必须在 `options` 内 |
| multiselect | 每个取值都必须在 `options` 内 |

必填集合 = `BASE_REQUIRED['generic']` ∪ 管理员勾选的自定义必填项；
**关闭采集的字段清空且不校验**；**未定义的 key 一律丢弃**（防伪造字段写入）。

**回环一致性**（`verify_generic.py` 覆盖）：导出模板的表头 = 固定字段标签 + 自定义字段标签，
导出后原样导入能自动匹配回同一批字段（自定义字段名已作为别名进入 `import_map` 的匹配表）。

## 5. 批量导入实现

`POST /api/applications/import`（multipart：`exam_id` / `audit_status` / `create_accounts`
/ `mapping` / `defaults` / `file`）

1. **表头识别**（见 §4.1 智能列识别）：自动探测表头行 → 模糊匹配每一列 →
   可在界面手工改判后由 `mapping` 回传覆盖
2. **数据转换**：`convert_row()` 逐行标准化（性别 / 证件类型 / 手机号 / 证件号 /
   省市区 / 科目·职业·学历·民族）
3. **整批默认值**：表里没有某必填列时（如考试机构编码），用 `defaults`（JSON）统一补齐
4. **必需列校验**：计算机 4 列，普通话 4 列，缺失直接整体报错
3. **逐行校验**：复用 `validate_computer` / `validate_mandarin`，与在线报名同一套规则
4. **范围强制**：`_apply_scope_defaults()` 校验导入行的「班级」必须落在班主任的管理班级列表内，
   班主任导入的数据无法越界到其他班级（未填班级时归入第一个管理班级）
5. **去重**：文件内证件号去重 + 本批次 `id_number` 去重
6. **自动建号**：`_ensure_student_user()` 以证件号去重，用户名 = 证件号后 8 位，
   初始密码 = 证件号后 6 位（不足 8 位补足）
7. **落库**：`import_batches` 记录批次汇总，`import_errors` 记录失败明细
8. **错误报告**：`GET /api/applications/import-batches/{id}/errors` 生成 xlsx

模板下载：`GET /api/applications/import-template?exam_id=` → Sheet1 表头 + 示例行，
Sheet2「可选值」列出机构编码 / 报考科目 / 从事职业 / 省市区 + 当前导入范围说明。

### 5.1 智能列识别（支持任意自定义表头）

模块：`backend/app/import_map.py`。目标是用户可直接上传花名册 / 教务导出，
不必改成官方模板格式。

**三层匹配**（`match_header()`，置信度递减）：

| 层级 | 规则 | 置信度 |
|---|---|---|
| 精确 | 归一化后与别名完全相同 | 1.00 |
| 包含 | 别名与表头互为子串，按长度占比给分 | 0.70~0.90 |
| 关键词 | 命中字段关键词（如「身份」「手机」） | 0.55 |

归一化 `norm()`：去空格 / 标点 / 星号 / 「（必填）」类括号内容 / 必填后缀，并转小写。
候选字段按 `exam_type` 限定（`fields_of()`），避免「学院」在两类模板间误判。

- `detect_header_row()`：前 5 行里挑命中字段最多的一行作表头（兼容首行大标题）
- `auto_map()`：逐列匹配，**同一字段只保留置信度最高的一列**，避免两列抢同一字段
- 预览接口 `POST /api/applications/import/preview` 返回逐列 `{col, header, field,
  confidence, samples}`、未识别列、缺失必填项，以及前 3 行**转换后**的样例
- 前端展示可信度徽章（精确 / 较可能 / 推测 / 未识别），可下拉改判；
  提交时把 `mapping`（`{列下标: 字段名}`）与 `defaults` 一并回传

**值转换** `convert_value()` / `convert_row()`：

- 省市县有级联依赖，`convert_row()` 按 省→市→县 顺序转换，保证上级已规范化
- 字典类字段用**重叠率**（`min(len)/max(len)`）选最贴切项，而非首个子串命中。
  这样「身份证」→`居民身份证`，而「香港居民身份证」不会被短名抢走判成 `1`
- 匹配不上则**原样返回**，交给后续 `validate_*` 报错，不静默改写用户数据

**踩坑**：`import_map.py` 位于 `app/` 包内，导入同包模块要用 `from . import db`
（写成 `from .. import db` 会报 `attempted relative import beyond top-level package`）。

## 6. 大数据量导出

`build_workbook(exam, rows, path, total)` 按行数自动分流：

| 条件 | 实现 | 特点 |
|---|---|---|
| `total <= 3000` | 常规 `Workbook` | 保留完整样式（表头填充/边框/冻结窗格/列宽） |
| `total > 3000` | `Workbook(write_only=True)` + 游标分批 | 内存恒定；表头用 `WriteOnlyCell` 带样式 |

关键点：

- `_collect_iter()` 用 `cur.fetchmany(1000)` 分批产出 dict，不把全表读进内存
- write_only 模式**只能用 `append()`**，因此辅助 Sheet 全部改为二维网格 `_grid_append()`，
  普通话 Sheet3 的「省级/市级/县区级」错列排布也用网格精确复刻
- 列宽 / 冻结窗格必须在 `append` 之前设置

实测（`tools/perf_export.py`，12000 行）：

```
流式导出 12000 行：耗时 6.84s，峰值内存 0.9 MB，文件 0.7 MB
端到端导出 12000 行：耗时 1.23s，响应 0.7 MB
```

save(data) {

- `_migrate()`：检测 `users` 表是否缺少 `grade` / `college` / **`department`** / `class_name` / `id_number`，
  缺则 `RENAME → 重建 → 回填 → DROP`，用于老版本数据库平滑升级
  （同时把 `role` 的 CHECK 约束扩展到 5 个角色）
- `_drop_type_checks()`：老库 `exams` / `audits` 上还有
  `CHECK (exam_type IN ('computer','mandarin'))`，会挡住自定义类型，
  这里检测 `sqlite_master.sql` 并在需要时重建表移除约束（保留全部数据）
- `_seed_exam_types()`：播种内置两套类型（`is_builtin=1`，不可删除）

### 9.3.1 启动器 `backend/launcher.py`（exe 入口）

双击 exe 时执行的就是它，职责：建 `data/` → 选端口 → 打印横幅 → 开浏览器 → 起 uvicorn。

| 参数 / 环境变量 | 作用 |
|---|---|
| `--port N` / `EXAM_PORT` | 指定端口（默认 8765，占用时自动顺延 30 个） |
| `--host H` / `EXAM_HOST` | 监听地址，默认取 `config.HOST`（`127.0.0.1`） |
| `--lan` | 强制 `--host 0.0.0.0`，优先于开关 |
| `EXAM_LAN=0` / `1` | 环境变量，显式给出时优先于 settings（自动化测试用） |
| 系统维护 → 局域网访问 | 写入 `settings.json` 的 `network.lan_access`，**默认 1（开启）** |
| `--no-browser` | 不自动开浏览器（服务器常驻时建议加） |
| `--seed-demo` | 写入演示数据 |

三个关键约定（改动时务必保留）：

1. **`0.0.0.0` / `::` 不能当访问地址**。`is_wildcard()` 判定「监听全部网卡」后，
   浏览器打开的地址一律换成 `127.0.0.1`，并把局域网网址列表另行打印。
   Windows 下直接打开 `http://0.0.0.0:8765` 是打不开的。
2. **局域网 IP 靠 UDP `connect()` 拿**，不是发包：`socket.connect(("223.5.5.5", 80))`
   后读 `getsockname()`，只查路由表，无网时静默降级为 `gethostname()` 解析。
   首个结果是默认出口网卡，标注「首选」；其余可能是 WSL / 虚拟网卡的地址。
3. **横幅必须 `flush=True`**。控制台下 stdout 是块缓冲，不加 flush 时用户
   在 exe 窗口里要等很久才看到访问地址（进程不退出就一直看不到）。

监听全部网卡时会额外打印安全提醒——此时同网段任何设备都能打开系统，
需提示修改初始密码与放行防火墙。

监听地址的最终取值优先级（改动时注意别让命令行参数被 settings 覆盖，或反之）：

```
--lan  >  --host  >  EXAM_LAN  >  settings.json network.lan_access  >  config.HOST
```

交付默认 `lan_access=1`（局域网默认开放，便于集中采集）；管理员可在
「系统维护 → 局域网访问」关闭。**监听地址在服务启动时就固定了**，
运行期改开关只能等下次启动才生效——后端 `/api/system/settings` 会在响应里回显
`listen`（当前 host/port/wildcard/lan_urls），前端据此提示「需重启」。

网络工具集中在 `backend/app/netutil.py`（`is_wildcard` / `lan_ips` / `valid_host` /
`access_urls`），启动器与后端共用，**避免两处显示的地址不一致**。

## 10. AI 智能分析与智能客服

对应代码：`backend/app/ai_engine.py`（引擎）+ `backend/app/routers/ai.py`（接口）
+ `backend/app/static/js/pages/ai.js`（页面）。

### 10.1 双层架构（零配置可用 + 可选增强）

| 层 | 实现 | 依赖 | 说明 |
|---|---|---|---|
| 本地规则引擎 | `ai_engine` 的统计 / 体检 / 客服部分 | 无 | 不联网、不装 SDK，exe 单机分发开箱即用 |
| 外部大模型 | `ai_engine.llm_chat()` | stdlib `urllib` | OpenAI 兼容 `/chat/completions` 协议 |

三条硬约束：

1. **可增强但不依赖**——未配置 / 超时 / 返回异常一律静默回退本地结果，
   `analyze()` 与 `chat()` 永远不会因大模型失败而抛错。
2. **只用标准库**——用 `urllib.request` 而非 `requests`，不给 PyInstaller 增加隐式依赖；
   且 `_opener_for()` 对本机地址（`127.*` / `localhost`）**绕过系统代理**——
   单位机器普遍配了 HTTP 代理，不绕过的话自建模型（Ollama / vLLM）调用必然失败；
   外网地址仍走代理，企业内网才能正常出网。
3. **权限与范围不绕过**——取数全部走 `analysis.build_scope()`（内含 `scope_filter`）；
   客服的数据类意图先做 `has_perm()` 判断，无权限时明确说明原因，而不是返回空数据。

### 10.2 配置存储（`data/settings.json` 的 `ai` 段）

复用既有的 `config.load_settings() / save_settings()`，不新增存储机制。

| 字段 | 默认 | 说明 |
|---|---|---|
| `enable` | 0 | 仅 1 时允许联网调用 |
| `base_url` | "" | OpenAI 兼容地址，必须以 http(s) 开头 |
| `api_key` | "" | **只写不读**：GET 一律返回掩码 `******` |
| `model` | "" | 模型名 |
| `timeout` | 30 | 5-120 秒 |
| `system_prompt` | "" | 可选，追加到系统提示词 |

密钥三态：`""` 与 `"******"` 表示**不修改**，`"__clear__"` 表示**删除**，其余值写入。
这一设计让前端无需取回明文密钥即可完成「保持 / 更新 / 清除」三种操作。

### 10.3 智能分析（`POST /api/ai/analyze`，需 `analysis` 权限）

```python
scope = build_scope(user, exam_id, exam_type)   # 已含数据范围收敛
rows  = _collect(scope)                          # 两张报名表合并取行
checks = _checks(rows, exams)                    # 11 类体检
```

| 输出 | 说明 |
|---|---|
| `overview` | 复用 `summary_of()`，另附 `exam_count` |
| `summary` | 本地拼写的自然语言结论 |
| `health` | `score`（0-100，按问题占比扣分）+ `level`（good/fair/poor）+ `checks` |
| `anomalies` | 有问题的检查项，按数量降序 |
| `bottlenecks` | 待审批次 / 积压数 / 平均审核小时 / 审核员工作量 / 临截止批次 |
| `trend` | 近 14 天 + 按月 |
| `suggestions` | 带 `action.path` 的可直达建议 |

## 11. 验证码网关与系统配置

### 11.1 设计原则：不许谎报「已发送」

早期 `issue_code()` 的短信分支只有一个标志位：

```python
delivery = "sms" if sms_configured() else "console"   # ← 从未真正调用网关
```

界面据此提示「验证码已发送至 139****」，用户却永远收不到。修复后：

- `sms_configured()` 收紧为「**配置齐全到可以真正发送**」才算已配置
  （阿里云要求密钥含 `:`、签名与模板齐全；通用网关要求地址与密钥齐全）；
- `_send_sms()` 真实发起 HTTP 请求，返回 `(是否成功, 原因)`；
- **发送失败一律降级为 `console`** 并打印网关原始错误，绝不谎报；
- 未配置时一个请求都不发。

### 11.2 两种网关

| provider | 鉴权方式 | 依赖 |
| --- | --- | --- |
| `aliyun` | 参数按字典序排序后 HMAC-SHA1 签名（AccessKeyId:AccessKeySecret） | 纯 stdlib：`hmac`/`base64`/`uuid`/`urllib` |
| `generic` | `Authorization: Bearer <api_key>` + JSON body | 同上 |

不引入任何第三方 SDK，避免给 PyInstaller 增加隐式依赖。

### 11.3 配置接口

```
GET  /api/system/settings     # 密钥只回掩码 ****** + xxx_set，另回 mail_configured/sms_configured
PUT  /api/system/settings     # 局部更新；密钥三态：掩码=不改、__clear__=删除、其余=写入
```

与 AI 配置的密钥处理保持同一套语义（`******` 不修改、`__clear__` 删除）。
前端入口在「系统维护 → 邮件 / 短信网关」卡片，保存即生效，无需重启。

### 11.4 测试要点

`verify_audit_fixes.py` 内起**模拟短信网关**（`start_sms_mock()`），断言：
请求确实发出、带了 Bearer 鉴权、body 含手机号与验证码；
未配置时 `delivery == "console"` 且**零请求**。
同 AI 模块一样——**「可选增强能力」必须连成功路径一起测**。

## 12. 字典维护、找回密码与代撤回

功能审计发现的「承诺了但没实现」或「能力存在但没有入口」，在本轮补齐。

### 12.1 字典维护（`/api/dicts/manage/{kind}`）

此前字典（考试机构 / 报考科目 / 从事职业）**只读**，管理员要新增只能重新生成 `dicts.json`。
实际上这三张表就是**实时数据源**——报名校验、导入匹配、表单下拉都直接查表，
所以只需补上 CRUD 即可让改动立即生效。

```
GET    /api/dicts/manage/{org|subject|occupation}?keyword=&page=&page_size=
POST   /api/dicts/manage/{kind}          # 新增
PUT    /api/dicts/manage/{kind}/{id}     # 改名
DELETE /api/dicts/manage/{kind}/{id}     # 删除（被引用则拒绝）
```

两条关键约束：

- **被引用不能删**：`_used_count()` 跨 `ET.ALL_APP_TABLES` 统计该值被多少条记录引用
  （只统计表内真实存在的列，通用表没有 `subject` 列也不会报错）；> 0 直接拒绝删除并告知数量
- **改名不改写历史**：明确提示「改名不会改写历史报名记录，导出仍以原值为准」，
  避免管理员以为「全改了」

前端新增 `pages/dicts.js`，路由 `/dicts`（`exam_manage` 权限），保存后调
`loadDicts(true)` 强制刷新全局字典缓存。

### 12.2 找回密码（`POST /api/auth/reset-password`）

《使用说明》一直写着「补充手机 / 邮箱便于后续找回密码」，但后端**没有对应接口**——
属于文档承诺未兑现。现已补齐：

1. `send-code` 的 `purpose` 增加 `reset`，且 `reset` 与 `register` 的**存在性校验相反**
   （注册要求「未被占用」，找回要求「必须已绑定」），未绑定时明确提示
2. `reset-password` 校验验证码 → 重置密码 → 重置失败计数与锁定
3. 前端登录页「忘记密码」弹窗：验证方式切换（手机 / 邮箱）+ 验证码 + 新密码 + 确认

> JWT 是无状态的，不存在 `refresh_tokens` 表，因此重置后直接清失败计数即可，
> 不要写 `DELETE FROM refresh_tokens`（表不存在会报错）。

### 12.3 管理员代考生撤回

`withdraw()` 原本只允许「本人撤回」，管理员遇到考生联系不上、又必须撤销的场景无从下手。
放开为：

```python
if row["user_id"] != user["id"]:
    # 非本人：必须有审核权限，且该记录落在自己的数据范围内
    if not has_perm(user, "audit"):
        raise ApiError("无权操作他人报名记录", code=403, status=403)
    _scope_guard(user, tbl, app_id)
```

**写操作同样要过范围守卫**——只让列表收敛是不够的，越权审核 / 撤回一样要被拦。
前端在审核详情抽屉里对「待审核」记录显示「代考生撤回报名」，并注明与「驳回」的区别
（撤回 = 删除记录，驳回 = 保留记录）。

## 12.6 实名认证（模块 11）

文件：`backend/app/realname.py`、`backend/app/routers/realname.py`、表 `realname_profiles`

```
realname_profiles(user_id UNIQUE, real_name, id_type, id_number,
                  status CHECK(pending|approved|rejected), channel, provider_uid, trans_id,
                  reviewer_id, reviewer_name, review_note, submitted_at, reviewed_at)
```

设计要点：

- **一人一条**：`user_id` 唯一，重复提交走 `UPDATE` 并回到 `pending`，不堆历史
- **脱敏**：对外一律 `_row_to_public(mask=True)`，证件号保留前 4 后 2
- **密钥只写不读**：支付宝 / 微信的 `private_key`、`alipay_public_key`、`app_secret`、
  `api_v3_key` 在 GET 时回 `******`；PUT 三态 —— `""`/`******` 表示不修改，
  `__clear__` 表示删除（早期只有两态会导致密钥永远删不掉）
- **第三方通道不伪造结果**：密钥未配齐时走 mock 并明确标注「演示」；
  `handle_callback()` 在通道未启用时直接报错，**绝不返回「已通过」**
- **两个落地点**：
  1. `routers/auth.py` 找回密码：先核验「已通过实名的证件号」，其次才是账号上的 `id_number`
  2. `routers/applications.py` 的 `submit()`：开启 `require_approved` 后调
     `RN.assert_can_apply(user)` 拦下未实名账号
- **保存校验**：关闭「允许本人自填」且没有任何第三方通道可用时直接 400，
  避免出现「谁都无法实名」的死局

前端：`pages/realname.js`（我的实名 / 第三方通道 / 管理员审核 / 实名设置）；
`pages/users.js` 增加「实名」列与「实名审核」入口（角标取 `/api/realname/list?status=pending` 的 total）。

## 12.7 汇总导出：官方模板填充与一键打包

文件：`backend/app/routers/export.py`

**两种表格来源**（`table_mode`）：

| 值 | 行为 |
|---|---|
| `template`（默认） | 复制官方模板副本，按**表头名称**定位列后写入 |
| `build` | 沿用原有自建表格 |

模板模式的关键实现：

- `_locate_header(ws, names)`：**按名称**建立「表头 → 列号」映射，最多扫前 8 行找表头行
  ——同一模板内数据列顺序可能 ≠ 标题列顺序（辽宁铁岭/朝阳颠倒、陕西杨凌示范区排到末列），
  按位置写必然错位
- 写入时 `cell._style = copy(...)` 保留原样式，其余 Sheet（填表说明、sheet3…）原样保留
- `TEMPLATE_MAX_ROWS = 20000`：openpyxl 需整本读入内存，超限自动退回自建模式
- 模板查找顺序：`data/templates/`（管理员上传）→ `backend/app/assets/templates/`（内置）
- 上传校验：必须有 `Sheet1` 且表头识别率 ≥ 1/2 才接受，否则拒绝并说明识别到/缺失哪些列

**一键打包**（`POST /api/export/bundle`）：

```
{考试名}/汇总表/{表格}.xlsx
{考试名}/证件照/{院系}/{班级}/{证件号码}.{jpg|png}
{考试名}/_导出说明.txt     ← 筛选条件、照片张数、未上传照片名单
```

- zip 内中文名必须 `ZipInfo.flag_bits |= 0x800`（UTF-8 标志位），否则 Windows 解压乱码
- PNG→JPG 转换**必须先铺白底**，Pillow 不能直接把 RGBA 存成 JPEG
- HTTP 头不能含非 ASCII：文件名走 RFC 5987 `filename*=utf-8''<urlencoded>`

## 12.8 数据大屏深度层

文件：`backend/app/routers/dashboard.py`

大屏是**轮询**接口（默认 30 秒），因此深度指标一律用 SQL 聚合，
不像 `/api/analysis/deep` 那样把全表行读进内存：

| 指标 | 实现 |
|---|---|
| 审核时效均值 | `AVG((julianday(reviewed_at)-julianday(created_at))*24)`，精确值走 SQL |
| 中位 / P90 / 分布 | 取明细（截断 5 万条）排序后计算，超大库退化为近似 |
| 证件照完整率 | `EXISTS (SELECT 1 FROM users u WHERE u.id=p.user_id AND u.photo<>'')` |
| 年龄分段 | `substr(id_number,7,4)` 取出生年，再按 `AGE_BUCKETS` 归并 |
| 驳回原因 | 只取 `rejected/returned` 的 `audit_comment`（单表 600 条封顶）做关键词归类 |
| 单位 → 班级 | `_ORG_SQL` 按模板取 `school/org_name`、`employer/department`、`college` 统一口径 |

> ⚠ **证件照完整率必须用 `EXISTS` 子查询而不是 `JOIN`**：数据范围片段 `scope_filter()`
> 返回的是不带表名的列名（`class_name` / `school`…），一旦 `JOIN users`，
> 两边同名列会让 SQLite 报 `ambiguous column name`。`EXISTS` 的子查询是独立作用域，不受影响。

前端 `pages/dashboard.js` 分三层渲染：总量 KPI（6）+ 过程 KPI（4）+ 深度面板（10 个），
并抽出 `hbar()` / `vbar()` 两个画法函数统一横向/纵向条形图样式。

### `api.js` 三种返回形状（取值前务必确认）

| 方法 | 返回 |
|---|---|
| `get` / `post` / `put` / `del` | **已解包的 payload**（直接用，不要再取 `.data`） |
| `upload(url, formData)` | `{ data, message }` |
| `uploadBlob(url, formData)` | `{ blob, headers, type }` |

> `idphoto.js` 曾因 `api.get` 后又取 `.data` 导致整个页面拿不到规格数据（详见踩坑记录）。

## 12.9 AI 服务商预设与连接诊断

文件：`backend/app/ai_engine.py`

- `PROVIDERS`：10 个预设（openai / deepseek / doubao / qwen / zhipu / moonshot /
  siliconflow / baichuan / ollama / custom），带 `base_url`、`models`、`key_hint`、
  `no_key`（本地免密钥）、`local`（永远直连）、`overseas`（需代理）标记
- `provider_of(base_url, provider)`：**以地址为准反查**，地址为空才退回保存的标记
  ——只看标记会出现「填了 deepseek 地址却提示 OpenAI 是境外服务」的误报
- `preflight()`：调用前参数自检，返回 `issues:[{field,label,hint}]`
- `llm_call()` 返回结构化 `{ok, stage, code, message, hint, text, latency_ms, meta}`；
  `HTTP_HINTS` 把 401/403/404/408/422/429/5xx 翻译成人话，`_diag_exc()` 把
  DNS / 拒连 / 超时 / 证书 / 代理异常也翻译成人话
- 404 且响应体含 `model` 时明确提示「模型不存在，本地服务可先用 `ollama list` 查看」
  ——本机 Ollama 未下载模型是最常见的失败原因
- `POST /api/ai/test` 接受未保存的配置（掩码 `******` 表示沿用已保存密钥），
  「测试连接」不必先保存

## 12.10 证件照制作（模块 12）

文件：`backend/app/idphoto/`（`specs.py` / `matting.py` / `maker.py`）、
`backend/app/routers/idphoto.py`、`backend/app/static/js/pages/idphoto.js`

独立功能栏「证件照制作」（左侧菜单，对所有登录用户开放），与「上传证件照」
共用同一套规格——上传处选尺寸底色时，走的就是这里的实现。

**双引擎**：

| 引擎 | 说明 |
|---|---|
| `local`（默认） | 内置 `hivision_modnet.onnx`（24.7MB）+ onnxruntime，**全程离线**，照片不出本机 |
| `remote`（可选） | 管理员在系统维护配置 HivisionIDPhotos 的 HTTP 接口；本地不可用时自动回退，反之亦然 |

接口：`GET /api/idphoto/specs`（尺寸/底色/引擎状态）、
`POST /api/idphoto/preview`（只抠图，返回透明 PNG）、
`POST /api/idphoto/make`（抠图 → 换底色 → 排版，直接返回图片，
响应头带 `X-IdPhoto-Engine` / `X-IdPhoto-Size`，文件名按 RFC 5987 回传中文名）。

**关键实现约定**：

- 抠图算法源自 HivisionIDPhotos（Apache-2.0），但**不引入 opencv / rembg / scipy**：
  原实现的 `cv2.resize` / `cv2.split` / `cv2.merge` 用 **Pillow + numpy** 等价替换
  （`INTER_AREA` → `Resampling.BOX`，放大用 `BICUBIC`）。这条重型依赖链会让
  单文件 exe 膨胀上百 MB
- 排版一律 **contain（等比缩放居中）**，宁可留边也不裁掉头部——裁头是证件照的硬伤
- **留白边填充照片自身的边缘色**（`_edge_color()`），不是硬填白：
  一寸 295×413（比例 0.714）对不上手机直出的 3:4（0.75），几乎必然留边，
  填白色会给一张蓝底照片套一圈突兀的白框
- 「不换底」（`color=keep`）走**免抠图快路径**：不加载模型、不联网，
  原尺寸 + 不换底时连重编码都省了，直接原样返回

> ⚠ **打包必须带模型资源**：`tools/build_exe.py` 需
> `--add-data app/assets/idphoto`（含 `hivision_modnet.onnx` 与许可证），
> 且 HIDDEN 含 `app.idphoto.*` 与 `onnxruntime`。**numpy 不能被排除**
> （早期为瘦身排除过，接入 onnxruntime 后运行时会 `ImportError`）。
> 模型没打进去时 `available()` 返回 False，前端会**静默退回远程引擎**，
> 页面上完全看不出来 —— 因此 `verify_packaged.py` 第 [9] 节直接断言
> `engines.local.enabled === true` 并**真的跑一次推理**（拿到 PNG 才算数）。

### 12.10.1 可调参数与「底部漏色」修复

抠图质量受原图影响很大（逆光、头发丝、衣服与原背景同色），固定参数必然顾此失彼。
因此把影响观感的三个量开放出来，**双层生效**：管理员设「初始化参数」，用户可在页面上调。

```python
PARAM_RANGES = {
    "alpha_threshold": (0, 255, 55),   # 抠图阈值：低于它的 alpha 直接丢掉
    "edge_feather":    (0, 60, 10),    # 边缘羽化：阈值到阈值+羽化的过渡带宽
    "bottom_fill":     (0, 60, 12),    # 底部补底：底部这么高的比例内，非纯主体一律压成全透明
}
BLANK_FILLS = ("edge", "white")        # 留白填充：取照片边缘色 / 硬填白
```

> ⚠ **`blank_fill` 只在「不换底」那档生效**。换底色时留白一律用所选底色 ——
> 底色是用户指定的纯色，整幅就该均匀，把原照片的背景色填进去反而变成一条色带。
> 「不换底」时照片是整张贴上去的，留白才需要跟它自己的背景衔接（填白会白得突兀）。

- `default_params()` 读 `data/settings.json` 的 `idphoto.params` 段（管理员在
  「系统维护 → 证件照初始化参数」里改，滑块 + 留白填充单选）；
- `norm_params(p)` 把前端传来的值夹回区间，缺失项回落初始化参数；
- 前端 `idphoto.js` 把用户调整存 `localStorage['idphoto.params']`，
  与初始化参数合并后随 `POST /api/idphoto/make` 的 `params` 字段提交；
- `GET /api/idphoto/specs` 一并返回 `params` 与 `param_ranges`，页面滑块区间不写死。

**留白取色不能用抠图后的图**：被抠掉的区域 `alpha=0` 且 RGB 通常是 `(0,0,0)`，
拿它求平均色会把留白填成**一圈纯黑**（`verify_idphoto.py` 的「角落像素」断言直接抓到）。
要取色就取**原图**，或者干脆用目标底色（换底时的正确做法）。

**底部漏色的根因**（用户实拍反馈）：

1. 早先 `_fill_blank_edges()` 把照片**四条边混在一起求一个平均色**再整块填充。
   证件照人像底部通常是深色衣服、两侧是浅色背景，混出来的颜色哪边都不像，
   填到底部就是一条突兀的色带。改为 `_side_colors()` **逐边取色**，
   上/下/左/右各自用自己的边缘色填自己那条边。
2. MODNet 输出的是软 alpha，衣服边缘常残留 20~80 的半透明像素，
   合成后还会透出原背景。新增 `matting.refine(rgba, threshold, feather, bottom_fill)`：
   把 alpha 从 `[threshold, threshold+feather]` 重新拉伸到 `[0,255]`（压实），
   再按 `bottom_fill` 把底部若干比例行内的非纯主体直接压成 0。

### 12.10.2 「调用我的照片」

证件照制作页的「调用我的照片」直接拉取本人已上传的证件照进编辑器：

```js
const res = await api.raw('GET', `/api/photos/${uid}`);
const f = new File([await res.blob()], `my-photo.${ext}`, { type: blob.type });
pickFile(f);
```

个人中心只做**单张原样上传**，不再在上传时抠图/换底 —— 需要特定尺寸底色时，
走「证件照制作 → 调用我的照片 → 做好后保存回个人中心」。
这样职责清楚：上传页不知道规格，制作页不负责存储。

## 12.12 注册页精简与验证方式开关

**页面只保留必填项**：账号、密码、手机号/邮箱（按所选验证方式显示）、验证码。
`real_name` 不再是注册必填（实名认证是独立模块 11，在个人中心里填）。

**验证方式由后台决定**，前端不能自作主张显示没开的通道：

```python
# config.py
"register": {"captcha": 1, "sms": 0, "email": 0}
```

- `GET /api/auth/verify-options?purpose=register` 严格按开关返回 `enabled`；
  找回密码（`purpose=reset`）不受注册开关限制，否则管理员关掉短信就没人能找回密码。
- `POST /api/auth/send-code` 在 `purpose != "reset"` 时校验
  `rg.get(verify_type)`，未开启直接 `403 管理员未开启该验证方式，无法发送验证码`。
- `register()` 对 `captcha` / `sms` / `email` 三路都做同样校验。
- 保存时**至少保留一种**（全关报「注册验证方式至少要保留一种」），
  读取时若配置残缺则兜底开 `captcha` —— 否则系统会把所有人锁在门外。
- 前端 `auth.js` 的 `options` 初值全 `enabled: false`（默认不能是「全开」：
  接口还没回来就先把通道露出来，等于谎报），取到结果后
  `form.verify_type = ['captcha','sms','email'].find(optOn) || 'captcha'`。
- 手机号走短信、邮箱走邮箱，网关未配置时系统维护页给出提示，
  但开关本身仍可开（开了没配网关，`send_code` 会诚实降级，不会谎报已发送）。

## 12.14 账号维度的数据范围校验

`scope_filter()` 收敛的是**报名记录**。但改资料、导证件照、看实名这类操作打在
**账号**上，以前只校验了权限组、没校验范围 —— 班主任拿着「批量导入」
就能按文件名给全校任何人换证件照。补两个函数：

```python
def can_access_user(operator, target) -> bool:          # 单条账号能不能碰
def user_scope_filter(operator, alias="u")              # users 表的范围片段（带别名）
```

`user_scope_filter()` 与 `scope_filter()` 是两套口径，**列名不一样**
（报名表院系列叫 `school` / `department` / `college`，账号表只有 `college`），
所以必须分开写，不能混用。

> ⚠ **`alias` 不是可选项**：`realname.py` 的列表是
> `realname_profiles p JOIN users u`，`users` 与报名表都有 `class_name`，
> 裸列名会让 SQLite 报 `ambiguous column name`。
> `user_scope_filter` 生成的片段一律带 `u.` 前缀。

同类问题也出现过大屏：`_reviewer_rank()` 的兜底分支写的是
`FROM {tbl} p LEFT JOIN users u ON u.id=p.reviewed_by{clause}`，
而 `clause` 里的 `class_name` 不带表名 —— 班主任（`scope_class`）打开大屏必现 500。
修法是**先把带范围过滤的报名表包成派生表再 JOIN**：

```sql
FROM (SELECT * FROM applications_computer WHERE 1=1 AND class_name IN (?,?)) p
LEFT JOIN users u ON u.id=p.reviewed_by
```

派生表是独立作用域，裸列名只落在子查询里，不会和外层的 `users` 撞。
**凡是 `clause` 与 JOIN 同时出现的地方都要这样处理**（`_photo_stats()` 用
`EXISTS` 子查询也是同一个道理）。

## 12.15 字典默认值（二级学院 / 部门）

`db.py` 的 `DEFAULT_COLLEGES` / `DEFAULT_DEPARTMENTS` / `DEFAULT_COLLEGE_DEPARTMENTS`
在**字典表为空时**灌入默认值；已有数据则不动，尊重管理员的删改。

三个常量**当前都是空列表**，即出厂不预置任何学院 / 部门。

> ⚠ 别再往里填具体院校的值：本仓库是公开的，预置什么就等于把使用单位的
> 院系设置与内设部门公开出去。曾经放过某校的 9 学院 + 18 部门，已全部移除。
> 部署方在「字典维护」里录入，录入后不会被重启覆盖（`_seed_dict_defaults` 只在表空时写）。

**层级是平铺单层**，不是树：`dict_department` 多一个 `college` 列，
部门只是「可归属到某个学院」，不做嵌套（`college` 为空 = 校级处室）。
老库缺列由 `_ensure_department_college_col()` 用 `ALTER TABLE ADD COLUMN` 补齐。

读写侧的三处约定：

- `EDITABLE["department"]` 用 **`extra: ("college",)`** 而不是把它塞进 `cols`。
  `cols` 同时用于 SELECT、关键词检索与 `_used_count()` 的取值；
  把 `college` 混进去，引用统计会拿**部门名**去报名表的院系列里比对，凭空造出引用数。
- `_norm_college()`：留空放行，非空**必须已在二级学院字典里**，否则 400。
  手打错字会让这个部门永远挂不到任何学院下面，还查不出来。
- 新增 `GET /api/dicts/department/full`（`[{id,name,college}]`）给账号编辑页用；
  老的 `GET /api/dicts/department` 仍只返回名称数组，`store.js` 两边都取。

账号编辑页（`users.js`）的 `deptOptions` 按所选学院过滤：
命中该学院的部门 + 全部校级部门（`college` 为空的永远可选），
标签带学院后缀（如「学工办（辅导员）（信息工程学院）」），
下拉仍 `allow-create`，不拦手工输入。

> **核心教训**：解析官方模板这类「人工排版」的表格时，**不要依赖行列顺序**——
> 同一份模板内部就可能自相矛盾（数据列顺序 ≠ 标题列顺序），且会有"特殊行/特殊列"
> （表头占一行、省直辖单位排到末列）。一律**按内容（名称）匹配**，并对异常位置做显式兜底。
> 交付前用 `tools/compare_samples.py` 对官方模板做**逐格比对**，才能发现这类"看起来对、实际错位"的问题。
